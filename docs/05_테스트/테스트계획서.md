# 테스트계획서

기준일: 2026-09-17 · 공통 검증 계획 · 실행 결과는 별도 테스트결과서에서 관리

## 1. 목적과 범위

같은 요구사항을 두 Retrieval 구현에 적용하고, 검색 방식의 차이가 근거와 답변에 미치는 영향을 비교한다. 기능 시험, Retrieval 평가, LLM 답변 평가, 운영 성능 시험을 구분한다. 코드에 테스트가 존재하는 것과 테스트가 통과한 것은 다르다.

현재 main 앱은 Hybrid다. 순수 BM25(Version A)와 ChromaDB(Version B) 비교 전에 A의 실행 경로를 확정해야 한다. Hybrid 결과는 `실행 방식=Hybrid`라고 따로 표시하고 BM25 단독 점수로 옮기지 않는다. 비교를 위해 코드나 엔진을 변경하는 작업은 이번 문서 정비 범위에 포함되지 않는다.

## 2. 비교 조건 고정

| 조건 | 동일하게 유지하거나 명시할 내용 |
|---|---|
| 데이터 | 같은 원본 집합·개정본·파일 해시, 같은 추출 결과·chunk 경계·metadata |
| 질문 | 같은 질문 ID·문구·순서·후속 질문 조건. 모호함·답 없음 사례도 포함 |
| 정답 | 사람이 원문에서 지정한 기대 문서·페이지/위치·필수 근거. 정답 없음 별도 표시 |
| LLM | 같은 provider·모델·temperature·출력 한도·연결 조건 |
| Prompt | 같은 규칙·템플릿·직렬화·버전/해시. 근거 내용만 Retrieval 결과에 따라 다름 |
| 출력 | 같은 답변 형식·출처 구조·거절 기준·인용 검증 |
| 검색 범위 | 같은 사용자 권한·선택 문서·문서 revision |
| 검색 예산 | 후보 수·최종 근거 수·token 예산·문맥 확장·재정렬 적용 여부를 동일하게 고정하거나 차이로 명시 |
| 측정 환경 | Python·패키지·하드웨어·데이터 규모·캐시 cold/warm·반복 횟수 기록 |
| 평가기 | 같은 RAGAS 버전·지표 구현·평가 LLM/Embedding·프롬프트와 판정 기준 |

BM25 자체에는 질문 Embedding이 필요하지 않지만 Vector 버전에는 필요하다. 이 비용은 엔진 차이로 기록하고 검색 시간에 포함하는 범위를 통일한다. 합격 임계값·질문 수·반복 횟수는 담당자가 평가 전에 확정하며, 결과를 본 뒤 유리하게 변경하지 않는다.

## 4. 평가 지표

### RAGAS — 도입 예정

현재 소스·의존성에서 RAGAS를 확인하지 못했다. 이번 작업에서는 설치·호출하지 않는다.

| 지표 | 쉬운 설명 | 준비할 자료 |
|---|---|---|
| Faithfulness | 답변의 주장이 제공된 근거로 뒷받침되는 정도 | 답변·검색 근거 |
| Answer Relevancy | 답변이 질문에서 요구한 내용에 얼마나 맞는지 | 질문·답변, 선택 평가기의 추가 입력 |
| Context Precision | 유용한 근거가 검색 결과의 앞쪽에 배치되는 정도 | 순서가 있는 검색 근거·질문·선택 지표에 따른 참조 답변 |
| Context Recall | 정답에 필요한 정보가 검색 근거에 얼마나 포함되는지 | 참조 답변/필수 근거·검색 근거 |

RAGAS 문서에서는 버전에 따라 Response Relevancy라는 표기도 사용한다. 실제 도입 시 버전과 지표 구현을 고정한다. 설명 근거: [RAGAS 공식 지표 안내](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/), [공식 기존 지표 설명](https://docs.ragas.io/en/v0.1.21/concepts/metrics/).

거절·오류·빈 답변을 조용히 평가에서 빼지 않는다. 사례 수·미계산 사유·거절 적절성을 별도로 기록한다. 네 지표의 단순 평균은 정의를 합의한 뒤 보조값으로만 사용하며 의료적 안전성 점수로 해석하지 않는다.

### 현재 코드가 제공하는 평가

- `mvp.evaluate`: 관리자가 작성한 JSONL의 `question`, `expected_sources`(document_name, 선택 page/quote), 선택 previous_question을 읽는다. 로컬 색인 검색의 기대 근거 회수율, 사례 통과 수, 중앙값·p95 시간을 계산한다. 최대 200개 질문. LLM 평가가 아니다.
- `mvp.evaluate_cases`: 코드에 정의된 합성 10개 사례를 로컬 임베딩으로 검색한다. 기본 답변은 fixture이므로 실제 Groq 품질 결과가 아니다. `--live`는 실제 LLM을 호출하므로 별도 실행 조건·승인이 필요하다.
- 관리자 진단: 한 질문의 검색 단계·저장 벡터·차단 이유를 확인한다. 이 결과는 RAGAS 점수가 아니다.
- 계획 지표: Hit@k, MRR, 필수 근거 누락, 잘못된 인용, 적절한 거절, 응답 시간. 두 버전 비교의 정의와 k는 실행 전에 고정한다.

## 5. 실행 절차와 완료 조건

1. 승인된 비식별 데이터와 정답표를 확정하고 파일 해시·코드 커밋·설정을 기록한다.
2. 문서 추출·chunk·metadata를 원문과 대조한다.
3. 동일 조건으로 검색 결과를 수집하고 사람이 적합성을 검토한다.
4. 공통 Prompt/LLM으로 답변을 생성하고 인용·거절·필수 내용 누락을 점검한다.
5. RAGAS 도입 이후에만 정의된 평가기를 실행한다. 외부 평가 서버로 원문을 보내는 경우 자료 처리 승인을 먼저 확인한다.
6. 실행 ID·질문 수·오류 수·평가 가능한 사례 수와 점수를 테스트결과서에 함께 기록한다.
7. 사전 합의된 통과 기준과 운영 검증을 만족했는지 담당자가 판정한다. 현재 합격 기준은 확인 필요다.

개발 환경에 의존성이 준비된 뒤 사용할 기존 명령:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check mvp tests
```

현재 환경에는 두 모듈이 없다. 문서 정비를 위해 설치하거나 전체 테스트를 실행하지 않았다. `mvp.evaluate`의 docstring에 나오는 `docs/search-cases.example.jsonl`은 실제 현재 파일이 아니므로 그대로 실행 예제로 사용하지 않는다.
