# 멘토 조언이 SCHAT에 어떻게 반영되었는지 점검

이 문서는 멘토가 조언한 내용과 현재 SCHAT의 코드·설계서·평가 결과를 비교한 점검 기록입니다.

먼저 결론을 쉽게 말하면 다음과 같습니다.

> 검색 방식을 비교하고 문서화하는 기술 작업은 대부분 진행됐고, 개선 WBS와 자동 회귀 테스트도 마련됐습니다. 다만 21건 전체 결과의 사람 확인, 정답 기준의 독립적인 2차 검수, 최종 답변 품질 확정, 담당자·목표일 확정은 아직 남아 있습니다.

## 1. 멘토 조언 반영 현황

| 멘토가 조언한 내용 | 현재 상태 | 쉽게 판단하면 |
|---|---|---|
| BM25·ChromaDB·Hybrid를 같은 조건에서 비교 | 완료 | 승인 질문 21건과 같은 문서·청크로 비교했습니다. |
| 검색 결과를 점수로 평가 | 완료 | Hit@10, MRR, Recall, Precision 등을 계산했습니다. |
| ChromaDB 점수가 낮은 이유 조사 | 완료 | ChromaDB 자체보다 MiniLM 임베딩의 영향이 크다는 것을 확인했습니다. |
| 더 나은 임베딩으로 재평가 | 완료 | Gemini Embedding 2로 바꾸자 ChromaDB Hit@10이 33.3%에서 95.2%로 상승했습니다. |
| 임베딩 모델·정규화·거리 방식 확인 | 완료 | MiniLM 384차원, L2 정규화, cosine 거리 등이 기록돼 있습니다. |
| 시스템 구조를 사람이 보기 쉽게 문서화 | 완료 | 시스템·검색·답변 구조 설계서가 있습니다. |
| 프롬프트를 코드와 분리해 관리 | 완료 | YAML 파일로 분리했고 버전과 해시를 관리합니다. |
| 사람이 확인한 정답과 자동 테스트 활용 | 대부분 완료 | 승인 Gold 21건이 있지만 독립적인 2차 검수가 부족합니다. |
| 검색 결과를 사람이 직접 확인 | 일부 완료 | 최종 비교 결과에서 5건의 명시적인 사람 검수 기록을 확인했습니다. |
| 사용자와 관리자 권한 분리 | 완료 | 관리자만 관리 화면을 사용하도록 분리돼 있습니다. |
| 주간 일정과 WBS 관리 | 일부 완료 | 완료 기준과 상태가 있는 WBS를 만들었고, 담당자·목표일은 팀 협의가 필요합니다. |
| NotebookLM 등 기존 서비스와 자체 개발 비교 | 대기 | 문서 조사만으로 결론 내리지 않고, 실제 서비스에 같은 질문과 자료를 넣어 직접 시험한 뒤 비교해야 합니다. |
| 작은 MVP를 먼저 완성 | 일부 완료 | 이미지 기능 등은 v1.0에서 제외했지만 전체 구조는 여전히 복잡합니다. |

## 2. 잘 진행된 부분

### 검색 비교의 기본 조건을 맞췄습니다

- 사람이 승인한 Positive Gold 21건을 사용했습니다.
- 보류한 11건은 점수에 포함하지 않았습니다.
- 같은 문서 2개와 같은 청크 147개를 사용했습니다.
- 같은 corpus fingerprint, 질문 처리, Top-k 조건을 사용했습니다.
- 실험 때문에 현재 Production 검색 구조를 바꾸지 않았습니다.

### 검색 점수가 왜 달라졌는지 확인했습니다

| 검색 방식 | Hit@10 | MRR | 쉽게 풀이 |
|---|---:|---:|---|
| Pure BM25 | 90.5% | 0.5822 | 병원 전문용어와 정확한 단어 검색에 강했습니다. |
| ChromaDB + MiniLM | 33.3% | 0.1093 | 현재 데이터에서 의미 검색 품질이 부족했습니다. |
| ChromaDB + Gemini Embedding 2 | 95.2% | 0.4337 | 임베딩을 바꾸자 검색 성능이 크게 개선됐습니다. |
| Current Hybrid | 95.2% | 0.7370 | 정답 근거를 더 앞쪽 순위에서 찾는 능력이 가장 좋았습니다. |

ChromaDB는 문장의 뜻을 직접 판단하는 AI가 아니라, 문장을 숫자로 바꾼 결과를 보관하고 비슷한 숫자를 찾는 저장소입니다. 따라서 검색 성능은 ChromaDB만의 문제가 아니라 숫자를 만드는 임베딩 모델의 영향을 크게 받습니다.

## 3. 현재 문제와 개선 방법

### 문제 1. 정답 기준이 완전히 독립적으로 만들어진 것은 아닙니다

Gold는 사람이 최종 승인했지만, 시스템이 찾은 후보 근거를 보면서 작성한 assisted review 방식입니다. 승인자 이름도 `boha`, `보하`, `뽀`로 나뉘어 기록돼 있으며, 별도 임상 전문가의 2차 검수 기록은 확인되지 않았습니다.

**개선 방법**

1. 검색 방식 이름과 순위를 가린 상태에서 다시 확인합니다.
2. 실패 문항과 중요 문항은 다른 검수자가 2차 확인합니다.
3. 승인자 이름, 역할, 날짜 표기를 하나의 방식으로 통일합니다.

### 문제 2. 21건 전체 검색 결과의 사람 확인 기록이 부족합니다

점수는 21건 전체에 대해 계산됐지만, 최종 비교 결과에 대한 명시적인 사람 검수 기록은 UAT-S01, UAT-S02, UAT-T01, UAT-T02, UAT-T11 다섯 건입니다.

**개선 방법**

- 우선 실패 문항 전체를 사람이 확인합니다.
- 성공 문항도 질문 유형별 대표 사례를 확인합니다.
- 가능하면 21건 전체를 한 화면에서 확인하고 판정을 남깁니다.
- 병원 원문은 저장하지 않고 질문, 청크 ID, 순위, 판정만 남깁니다.

### 문제 3. 세 검색 방식이 완전히 한 가지 조건만 바꾼 비교는 아닙니다

BM25-only와 ChromaDB-only는 검색 결과를 그대로 평가했지만, Current Hybrid에는 BM25, MiniLM, FAISS, RRF, reranker, context expansion이 함께 사용됩니다.

따라서 현재 비교는 **실제로 사용할 세 가지 운영 전략 비교**로는 의미가 있지만, **검색 저장소 하나만 바꿔 비교한 실험**은 아닙니다.

**개선 방법**

- 현재 결과에 `운영 전략 비교`라고 명확히 표시합니다.
- 멘토가 순수한 엔진 비교를 원하면 context expansion 등을 같게 끔 추가 evaluation-only 실험을 합니다.
- 현재 Production Hybrid는 실험 때문에 변경하지 않습니다.

### 문제 4. 검색은 개선됐지만 최종 답변 품질은 아직 확정되지 않았습니다

현재 남은 문제는 검색보다 답변 생성과 안전 검증에 가깝습니다.

- UAT-T12: `즉시 운반하며 확인`의 `즉시`를 확인 행위까지 잘못 붙이던 오탐을 행위 구간 분리로 수정했습니다. 과거 후보의 검사 시행 누락 사람 판정은 별도로 유지합니다.
- UAT-T11: 반드시 들어가야 할 사실이 빠진 문제가 남아 있습니다.
- Faithfulness와 Answer Relevancy의 정식 평가가 완료되지 않았습니다.
- 전체 자동 테스트의 기존 실패 3건은 테스트 격리 문제로 확인해 수정했고, 현재 **985 passed, 5 skipped, 실패 0건**입니다.

그러므로 **검색 기준선은 상당히 안정적**이지만, **SCHAT 전체 v1.0은 아직 최종 READY가 아닙니다.**

## 4. 멘토 설명을 이해할 때 주의할 점

멘토의 전체 방향은 맞지만 다음 부분은 좀 더 정확히 구분해야 합니다.

- ChromaDB나 벡터 검색이 항상 BM25보다 좋은 것은 아닙니다.
- BM25는 문장을 임베딩 벡터로 바꾸지 않고 단어 출현 정보를 사용합니다.
- cosine similarity 0.9는 `정답일 확률 90%`를 의미하지 않습니다.
- ChromaDB 성능은 임베딩 모델, 청크 구성, 질문 처리, 거리 방식의 영향을 받습니다.

## 5. 앞으로의 우선순위

1. 완료: 기존 전체 테스트 실패 3건을 정리하고 전체 회귀를 통과했습니다.
2. T12 검사 오탐 수정은 완료했고, T11 답변 누락은 분리해 진행합니다.
3. 최종 검색 비교 21건 중 실패 문항 전체와 대표 성공 문항을 사람이 확인합니다.
4. Gold를 검색 방식이 보이지 않는 상태에서 독립적으로 재검수합니다.
5. 완료: Faithfulness와 Answer Relevancy는 외부 전송 승인 전 pending으로 두는 평가 계약을 확정했습니다.
6. 날짜·담당자·완료 기준이 보이는 간단한 WBS를 만듭니다.
7. 대기: NotebookLM 등 기존 서비스를 직접 시험한 뒤 자체 SCHAT와 같은 조건으로 비교합니다.
8. 이 결과를 바탕으로 v1.0 READY 여부를 다시 판정합니다.

## 6. 현재 판정

| 구분 | 판정 |
|---|---|
| 텍스트 검색 기준선 | Current Hybrid로 잠정 고정 가능 |
| ChromaDB 평가 | 임베딩 모델에 따라 결과가 달라짐을 확인 |
| 답변 생성 안전성 | 추가 정리 필요 |
| 21건 검색 결과의 사람 검수 | 일부만 완료 |
| SCHAT v1.0 최종 준비 | 아직 READY 아님 |

## 7. 개선 실행 WBS

WBS는 `누가, 무엇을, 언제까지, 어떤 결과로 완료할지`를 한눈에 보는 작업표입니다. 현재 확정되지 않은 담당자와 목표일은 추측하지 않고 `미정`과 `팀 협의`로 표시했습니다.

| 우선순위 | 해야 할 일 | 완료 기준 | 담당자 | 목표일 | 상태 | 결과 확인 |
|---:|---|---|---|---|---|---|
| 1 | 기존 전체 테스트 실패 정리 | 기존 실패와 실행 환경 문제를 구분하고 전체 테스트 결과를 다시 기록 | Codex 자동 작업 | 2026-09-21 | 완료 | Full pytest 985 passed, 5 skipped, 실패 0건 |
| 2 | UAT-T12 행위·강도 오탐 확인 | 실제 임상 의미 변경과 평가 검사 오탐을 구분 | Codex 자동 작업 | 2026-09-21 | 완료 | 행위 구간 결합 수정, 관련 49 tests passed |
| 3 | UAT-T11 필수 사실 누락 해결 | 제제별 시간·속도·행위의 관계가 빠지거나 섞이지 않음을 확인 | Codex 자동 작업 | 외부 호출 승인 후 | 사람 확인 필요 | Prompt 로컬 보강 64 tests passed, Live 재평가 대기 |
| 4 | 검색 결과 사람 검수 보강 | 실패 문항 전체와 질문 유형별 대표 성공 문항을 확인 | 사람 검수자 | 팀 협의 | 사람 확인 필요 | 21건 중 5건 저장, 로컬 검수 앱 준비 |
| 5 | Gold 독립 재검수 | 검색 방식과 순위를 가린 상태에서 2차 검수하고 승인자·일자를 기록 | 독립 검수자 | 팀 협의 | 사람 확인 필요 | Gold 승인 기록 |
| 6 | RAGAS·Live 평가 범위 확정 | Faithfulness·Answer Relevancy의 측정 가능 여부와 평가 방법을 결정 | Codex 자동 작업 | 2026-09-21 | 완료 | `RAGAS_Live_평가_범위.md` |
| 7 | 기존 서비스와 자체 SCHAT 비교 | 같은 승인 질문·문서·평가 기준으로 기존 서비스를 직접 시험하고 SCHAT와 결과를 비교 | 사람 확인 및 외부 서비스 사용 필요 | 팀 협의 | 대기 | 실제 서비스 테스트 전에는 비교 결론을 내리지 않음 |
| 8 | v1.0 최종 판정 | 검색, 답변, 안전, 사람 검수, 전체 테스트 결과를 합쳐 READY 여부를 확정 | 팀 책임자 | 선행 항목 완료 후 | 차단 | 사람 검수와 Live 재평가 대기 |

### 상태 표시 방법

- **대기**: 아직 시작하지 않음
- **진행 중**: 담당자가 작업하고 있음
- **사람 확인 필요**: 자동 검사는 끝났지만 사람 판정이 남아 있음
- **완료**: 완료 기준을 만족하고 결과 기록이 있음
- **차단**: 안전 문제나 필수 조건 미충족으로 다음 단계를 진행할 수 없음

WBS는 작업을 시작할 때 담당자와 목표일을 채우고, 완료할 때 상태와 `결과 확인` 항목을 같이 갱신합니다.

> 이 점검은 현재 코드와 저장된 평가 기록을 기준으로 했습니다. 병원 지침 원문, 환자정보, API 키, 외부 AI의 전체 응답은 포함하지 않습니다.
