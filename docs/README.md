# SCH Guide AI 표준 산출물 관리

기준일: 2026-09-17 · 문서 상태: 코드 기준 초안, 담당자 검토 전

## 1. 하나의 프로젝트, 하나의 정본

SCH Guide AI는 병원 직원이 등록 지침을 검색하고 근거가 있는 답변과 출처를 확인하는 하나의 프로젝트다. Version A(BM25 기반)와 Version B(ChromaDB 기반 Vector Retrieval)는 검색 방식 비교를 위한 구현 버전이며, 별도 프로젝트가 아니다.

목적·요구사항·화면·사용자 기능·데이터 처리·사용자매뉴얼은 하나만 관리한다. Retrieval, Embedding, Vector DB, 검색 파라미터와 평가 결과처럼 실제 차이가 있는 곳에만 버전별 칸을 둔다. 현재 브랜치에서 확인한 공통 처리라도 다른 버전이 동일하게 구현했는지는 그 담당자의 확인이 필요하다.

## 2. 작업 시작 시 확인한 기준선

| 점검 | 확인 결과 |
|---|---|
| 현재 브랜치 | `main` |
| HEAD | `8c448516b9eda5cab9acd5624d04837fc2a8a439` |
| 실제 Retrieval | BM25 + Vector의 Hybrid. 로컬 FAISS, 직원 운영 Supabase pgvector |
| ChromaDB | 현재 소스·의존성에서 미확인. 담당 브랜치와 구현 상태 확인 필요 |

| 현재 HEAD의 표준 산출물 | 8종 구조 없음. 기존 루트 README는 유지 |
| 공유받은 문서 이력 | 아래 다른 브랜치의 문서는 로컬 Git에서 읽을 수 있으나 현재 main에는 반영되지 않음 |
| 기존 미커밋 변경 | `mvp/app.py`, `mvp/ui.css`, `mvp/ui.py`. 현재 화면 설명에 반영하되 이번 문서 작업의 코드 변경으로 기록하지 않음 |
| 기타 기존 파일 | 미추적 `.agents/` 유지. 개인 스킬과 개발 산출물은 별개 |

이번 조사는 로컬 작업 트리와 이미 있는 remote-tracking ref를 대상으로 했다. `git fetch`를 실행하지 않았으므로 원격의 최신 상태를 보증하지 않는다. 실제 운영 DB·로그인 정보·원본 지침·비밀 설정 값은 조사하지 않았다.

### 기존 브랜치 문서 보존 및 참조

| Git 참조와 커밋 | 기존 문서 | 취급 |
|---|---|---|
| `origin/codex/two-stage-rag-plan` / `12b48f8` | `docs/00_PROJECT_GOAL.md`, `01_BM25_PLAN.md`, `02_BM25_RESULT.md`, `CHANGELOG.md` | BM25 일괄 평가의 기존 목표·계획·결과·이력. 다른 브랜치에서 관리 |
| `origin/boha-rag` / `dbad812` | `docs/bm25/01_PLAN.md`~`06_TEMPORAL_RERANK_RESULT.md`, `docs/rag/`의 설계·평가 문서 | 검색 개선 및 RAG 실험 이력. 다른 브랜치에서 관리 |

기존 문서는 삭제·수정·복제하지 않았다. 위 경로는 현재 작업 트리 링크가 아니라 Git 내부 경로다. 예를 들어 `git show 12b48f8:docs/00_PROJECT_GOAL.md`로 읽는다. 이전 목표 문서의 ‘등록 지침 근거만 사용’ 원칙은 공통 요구사항에 반영했다. 해당 브랜치만의 일괄 평가 화면이나 후속 실험 결과는 main의 구현·성적으로 옮기지 않았다.

## 3. 수정·Merge 규칙

1. BM25 담당자는 BM25 구현 기록을, ChromaDB 담당자는 ChromaDB 구현 기록을 실제 증거로 갱신한다. 다른 버전 기록을 임의 변경하지 않는다.
2. 공통 내용은 공통 요구사항이나 실제 기능이 바뀔 때만 수정한다. 요구사항 ID를 버전별로 복제하지 않는다.
3. 확인 불가능한 내용은 ‘확인 필요’, 다른 브랜치에만 있는 내용은 ‘다른 브랜치에서 관리’로 표시한다. ‘팀원 작업 중’은 담당자 확인 후 사용한다.
4. 코드에 없는 기능은 ‘미구현’, 도입 의사가 있는 RAGAS는 ‘도입 예정’으로 표시한다.
5. Merge 시 한쪽 docs 전체를 다른 쪽으로 덮어쓰지 않는다. 공통 정본을 기준으로 버전별 절과 실행별 결과를 합친다. 기존 세부 실험 문서는 History로 보존하고 정본에서 참조한다.
6. 동일 개념의 기존 REQ/화면/테스트 ID가 합류하면 담당자가 대응표를 검토한 뒤 하나로 통합한다. `*_BM25.md`, `*_ChromaDB.md` 정본을 새로 만들지 않는다.
7. 변경 날짜·근거 커밋·미커밋 여부·실행 조건을 기록한다. 예정 점수와 실행하지 않은 테스트의 통과 기록은 금지한다.
8. API Key, Password, Token, 환자 식별정보, 내부 지침 원문을 문서에 넣지 않는다. 결과 원본은 접근이 통제된 위치에서 관리하고 정본에는 식별자와 요약만 남긴다.

## 4. 검토가 필요한 사항

- Version A 비교 대상을 순수 BM25로 확정할지, 현재 Hybrid를 별도 기준선으로 기록할지 확인한다. 현재 Hybrid의 점수를 순수 BM25 점수로 쓰면 안 된다.
- ChromaDB 담당 브랜치·커밋·담당자를 확인하고 동일 데이터·화면·생성 계약 적용 여부를 대조한다.
- 현재 미커밋 UI 변경을 포함해 문서화했으므로 Git 업로드 전 코드와 문서의 기준선을 맞춘다.
- RAGAS 설정, 정답 데이터셋, 평가 실행과 승인 담당자는 아직 확정되지 않았다.
- 테스트 실행 결과는 [테스트결과서](06_테스트결과/테스트결과서.md)의 범위를 따른다.
