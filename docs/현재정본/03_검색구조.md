# SCHAT 검색 구조

## 현재 구성

| 구성 | 현재 상태 | 역할 | 비고 |
|---|---|---|---|
| BM25 | **Production** | 질문과 문서의 단어 일치를 이용한 빠른 lexical 검색 | Exact 의학 용어·제품명·수치 질문에 강함 |
| MiniLM | **Production** | 의미가 비슷한 문장을 찾는 semantic/vector embedding | `paraphrase-multilingual-MiniLM-L12-v2`, 384d |
| RRF | **Production** | BM25 순위와 의미 검색 순위를 rank 기반으로 결합 | Raw score를 직접 더하지 않음 |
| 기존 reranker | **Production** | 결합 후보를 topic·phase·lexical 규칙으로 다시 정렬 | E5 후보와 결합 시 성능 저하 원인 분석 pending |
| multilingual-e5-large | **Evaluation only** | retrieval 전용 다국어 embedding | 1024d, query/passage prefix, production 미사용 |
| ChromaDB | **Evaluation only** | Vector를 저장하고 유사도 검색을 수행하는 DB | Production catalog/DB를 대체하지 않음 |
| E5 vector snapshot | **Evaluation only** | 105개 passage를 재임베딩하지 않고 로컬 평가 재사용 | 원문·질문 미포함, production 미사용 |
| Table retrieval | **Evaluation only** | 구조화된 표의 header+row를 로컬에서 검색 | 5 tables/33 rows, production 미연결 |
| Image routing | **Pending** | 이미지·도식 근거가 필요한 질문 후보 표시 | 임상 해석과 answerability에는 미연결 |

## 자주 혼동하는 용어

- **BM25**는 단어 출현과 희소성을 이용해 문서를 점수화하는 검색 알고리즘이다.
- **E5-large**는 문장을 숫자 벡터로 바꾸는 retrieval embedding 모델이다.
- **ChromaDB**는 그 벡터를 저장하고 가까운 벡터를 찾는 vector database다.
- 따라서 BM25와 ChromaDB는 같은 종류가 아니며, E5-large와 ChromaDB도 서로 다른 역할이다.
- 현재 production은 ChromaDB나 E5-large로 교체되지 않았다.

## Production 검색 흐름

```text
질문 정규화와 QueryPlan
   ├─ BM25 후보
   └─ current MiniLM semantic/vector 후보
            ↓
          RRF 병합
            ↓
       기존 reranker
            ↓
  evidence gate/context 확장
```

관련 파일:

- 질문 분석: `mvp/query.py`
- Embedding 질문과 chunk: `mvp/library.py`
- BM25, RRF, reranker: `mvp/retrieval.py`
- Parent context: `mvp/context.py`
- Evidence gate: `mvp/evidence.py`

## 수혈 동일 조건 평가

평가 조건은 수혈 105 chunks, `transfusion-retrieval-v3` 90문항, approved positive 78문항, 동일 gold와 Top-K다. Negative 11문항과 human-review 1문항은 positive aggregate에서 제외했다.

| 전략 | Hit@10 | MRR | Recall@10 | Mean/P95 latency |
|---|---:|---:|---:|---:|
| BM25 current | 0.8846 | 0.5602 | 0.8379 | 1.010 / 1.628 ms |
| Current MiniLM vector | 0.2821 | 0.0913 | 0.2564 | 이전 공정성 평가 기준 18.651 / 24.872 ms |
| E5-large only | 0.9359 | **0.7151** | 0.9084 | 193.474 / 282.720 ms |
| BM25 + E5 RRF | **0.9487** | 0.6769 | **0.9359** | 194.651 / 283.856 ms |
| RRF + existing reranker | 0.9103 | 0.5184 | 0.8681 | 265.158 / 372.321 ms |
| Selective E5 | 0.9103 | 0.5997 | 0.8764 | 87.778 / 270.402 ms |

## 왜 E5/RRF를 바로 Production에 넣지 않았나

- Raw retrieval에서는 E5와 BM25+E5 RRF가 더 정확했다.
- 그러나 existing reranker를 적용하면 core 개선이 BM25 대비 +0.0131로 작아졌다.
- E5는 model cache 약 2.25GB, process RSS 증분 약 1.54GB와 평균 약 193ms의 query 비용이 든다.
- Selective fallback도 40/90문항에서 실행됐지만 best raw retrieval에 못 미쳤다.
- 따라서 validator나 reranker를 우회하지 않고 현재 production 구조를 유지했다.

최종 판정은 **E — 기존 production hybrid 유지**다.

## Runtime과 snapshot

| 항목 | 평가값 |
|---|---:|
| E5 model load | 4,424.18 ms |
| Model cache | 2,252,997,322 bytes |
| Process RSS model delta | 1,541,464,064 bytes |
| Passage build reference | 98,965.40 ms |
| Persistent snapshot | 389,672 bytes |
| Snapshot reload | 11.46 ms |

Snapshot은 105개 chunk ID, 105×1024 vectors와 계약 metadata만 가지며 원문과 질문을 포함하지 않는다. Local evaluation cache일 뿐 production asset이 아니다.

## 다음 검색 과제

1. Existing reranker가 E5 semantic 후보의 MRR을 떨어뜨리는 조건을 evaluation-only로 분해한다.
2. Exact term/fact-specific에서는 BM25의 강점을 유지하면서 procedure·temporal·paraphrase에서 E5 이득을 얻을 수 있는지 검증한다.
3. Production 변경은 end-to-end latency, memory, regression과 safety gate를 모두 통과한 뒤 별도 승인한다.
